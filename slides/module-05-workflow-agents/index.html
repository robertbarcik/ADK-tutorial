Workflow agents

Control flow as Python classes, not graph diagrams

Sequential · Parallel · Loop

One agent

Enough for toy problems.

Real work

Needs composition.

Three first-class primitives

  • SequentialAgent — run children in order. A shell pipeline.
  • ParallelAgent — run children concurrently. An asyncio.gather().
  • LoopAgent — cycle until exit_loop or max_iterations. A while with an escape hatch.

This is ADK's strongest pedagogical differentiator. LangGraph makes you draw a graph; CrewAI hides flow behind a role DSL; ADK lets you name the workflow.

Visual

SequentialAgent        ParallelAgent          LoopAgent
─────────────────      ─────────────────      ─────────────────
                                              ┌────────────────┐
   child 1                 child 1            │   child 1      │
      │                       │               │      │         │
      ▼                       ▼               │      ▼         │
   child 2          ──>   child 2   <──       │   child 2      │
      │                       │               │      │         │
      ▼                       ▼               │      ▼ (loop)  │
   child 3                 child 3            │   child 1 ...  │
                                              └────────────────┘
   ordered              concurrent           until exit_loop
   pipeline             fan-out              or max_iterations

State is the pipe

  • output_key="summary" on a child → writes its result to state["summary"].
  • {summary} in a later child's instruction → substituted from state before the model sees it.
  • {summary?} → same, but "optional; don't error if missing."

Write with output_key=. Read with {key}. No orchestration code.

Primitive 1

SequentialAgent

Ordered pipeline. State flows downstream.

A two-step pipeline

summarizer = LlmAgent(
    name="summarizer",
    instruction="Summarize the user input in one sentence.",
    output_key="summary",       # writes state["summary"]
)

translator = LlmAgent(
    name="translator",
    instruction="Translate to Slovak: {summary}",   # reads state["summary"]
    output_key="translation",
)

pipeline = SequentialAgent(
    name="pipeline",
    sub_agents=[summarizer, translator],
)

Primitive 2

ParallelAgent

Concurrent fan-out. Wall time ≈ slowest child.

Three-way fan-out

de_researcher = LlmAgent(name="de_researcher", ...,
    instruction="One fun fact about Germany.",
    output_key="germany_fact")
sk_researcher = LlmAgent(name="sk_researcher", ...,
    instruction="One fun fact about Slovakia.",
    output_key="slovakia_fact")
cz_researcher = LlmAgent(name="cz_researcher", ...,
    instruction="One fun fact about Czech Republic.",
    output_key="czech_fact")

trio = ParallelAgent(
    name="trio",
    sub_agents=[de_researcher, sk_researcher, cz_researcher],
)

What to notice

  • Authors interleave in finish order, not declaration order.
  • Wall time is one child's duration, not the sum. Savings scale with width of the fan-out.
  • Each child writes to its own state key, so they don't collide.

Common production pattern: fan out independent research in parallel, then feed everything into a Sequential synthesizer.

Primitive 3 · the canonical ADK wow demo

LoopAgent

Generator + Critic. Refine until satisfied.

The pattern

┌─ LoopAgent ──────────────────────────────────────────┐
│                                                       │
│   generator ─▶ writes state["draft"]                  │
│        ▲                                              │
│        │                                              │
│   critic ─▶ either writes state["critique"]           │
│             or calls exit_loop()                      │
│                                                       │
└──── repeat until exit_loop OR max_iterations ────────┘

Self-correction, critic-driven refinement, reflexion — same pattern, many names. In ADK: a LoopAgent with two children.

The generator

generator = LlmAgent(
    name="generator",
    instruction="""Write or revise a tagline.
If a previous draft and critique exist, revise
to address the critique. Otherwise, draft fresh.

Previous draft:    {draft?}
Previous critique: {critique?}

Output only the new tagline.""",
    output_key="draft",
)

? suffix = optional. On iteration 1 neither key exists yet.

The critic

critic = LlmAgent(
    name="critic",
    instruction="""Draft: {draft}
If the draft FAILS any criterion, write
one-sentence critique.
If the draft PASSES all criteria,
call exit_loop. Do NOT output text.""",
    output_key="critique",
    tools=[exit_loop],   # ← the exit-the-loop tool
)

refiner = LoopAgent(
    sub_agents=[generator, critic],
    max_iterations=5,    # safety net; always set
)

What to always do

Always set max_iterations

The critic might be impossible to satisfy. The agent enters an infinite loop; you get a big bill and no result. Set a ceiling.

Pair exit_loop with the child that has the exit condition

Usually the critic, reviewer, or gate-keeper. Don't scatter exit_loop across multiple children unless you mean to.

Use {key?} for keys that might not exist yet

Iteration 1 has no critique yet. Optional-state syntax avoids the error.

Putting it together

Composing workflows

Workflow agents are themselves agents.

Parallel inside Sequential

pipeline = SequentialAgent(
    name="research_pipeline",
    sub_agents=[
        trio,           # ParallelAgent: fan out 3 researchers
        synthesizer,    # LlmAgent: reads all 3 state keys, writes a report
    ],
)

Five LLM calls — three parallel researchers, then one synthesizer. Wall time ≈ two calls, not five. Production agents are built out of compositions like this.

Notebook cell 18

Workflow agent vs. LLM-driven flow

Workflow agent

  • Control flow is fixed
  • Determinism: tests & evals
  • Latency: Parallel fans out without a deliberation turn
  • Auditable from a diagram
vs

LLM-driven flow

  • Control flow depends on user input
  • Flexibility: the model's judgment is the point
  • Conversation can go anywhere
  • (M06 covers this — sub_agents and AgentTool)

The rule of thumb

If you can name the workflow, use a workflow agent.
If you can't, let the LLM decide.
