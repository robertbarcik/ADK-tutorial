All three produce the same thing at the agent layer. They differ only in who runs the container and what batteries come with it.

The foundation

The deployable repo layout

One folder, one agent.py, one root_agent.

The shape every tool expects

my_agent/
├── __init__.py          # empty; makes it a package
├── agent.py             # exports `root_agent`
├── requirements.txt     # pinned Python deps
└── .env                 # optional; OPENROUTER_API_KEY etc.

adk api_server, adk web, adk deploy cloud_run, AgentEvaluator.evaluate — all of them look for root_agent in agent.py.

Convention, not hard requirement. adk create scaffolds it for you.

Path 1

adk api_server

See your agent as an HTTP service locally.

Start it

# From the parent of the agent folder
adk api_server .

# Starts a FastAPI server at http://localhost:8000
# Hosts every agent folder it finds (each must have agent.py → root_agent)

Hit it

# Discover what's hosted
curl http://localhost:8000/list-apps

# Create a session, send a message, get events
curl -X POST http://localhost:8000/run \
  -H "Content-Type: application/json" \
  -d '{"app_name": "my_weather_agent", "user_id": "u", "session_id": "s1",
       "new_message": {"role": "user", "parts": [{"text": "Weather in Prague?"}]}}'

Path 2

Vanilla Docker

Deploy to any container platform.

The Dockerfile — 10 lines

FROM python:3.12-slim

WORKDIR /app

COPY my_agent/requirements.txt ./requirements.txt
RUN pip install --no-cache-dir -r requirements.txt

COPY my_agent/ ./my_agent/

ENV PORT=8080
CMD ["sh", "-c", "adk api_server /app --host 0.0.0.0 --port ${PORT}"]

No ADK-specific platform code. Just FastAPI-in-a-container. Deploys anywhere containers run.

Where you can ship the image

  • AWS Fargate / App Runner — aws ecr push, point a service at the image.
  • Azure Container Apps — az acr build, az containerapp create.
  • Fly.io — fly launch --dockerfile ./Dockerfile.
  • Kubernetes — your usual Helm chart or Kustomize manifest.
  • Your own server — docker run.

The important property: there's no ADK-specific deployment story for non-Google clouds. Regular container deployment.

Path 3

adk deploy cloud_run

One command. Minutes to prod.

The one-liner

adk deploy cloud_run \\
    --project YOUR_GCP_PROJECT \\
    --region europe-west1 \\
    --service_name my-weather-agent \\
    my_weather_agent

Under the hood: ADK generates a Dockerfile, builds via Cloud Build, pushes to Artifact Registry, deploys a Cloud Run service.

Pro: fast path on GCP; sensible defaults; integrates with Cloud Trace + Cloud Logging.
Con: Google Cloud only; less control; pay the Cloud Run runtime margin.

Path 4 (mention only)

Vertex AI Agent Engine

The opinionated managed path.

What Agent Engine adds over Cloud Run

  • Managed sessions — no separate database needed.
  • Memory Bank — LLM-distilled long-term memory, auto-consolidation, auto-decay. Real upgrade over M08.
  • Agent Identity — per-agent IAM principals with certificate-bound creds. Strongest enterprise-governance primitive Google ships.
  • Built-in evaluation + observability — integrates with Gen AI Evaluation Service.

Pricing picture (April 2026)

One more thing

Plugins

The production cross-cutting mechanism.

Callbacks vs Plugins

Callbacks (M07)

  • Per-agent
  • Attached to LlmAgent(...)
  • Good for agent-specific guards
vs

Plugins

  • Whole Runner, all agents
  • Attached to Runner(..., plugins=[...])
  • Good for org-wide policy

Rule: callbacks for agent-specific logic; plugins for app-wide policy. Audit logging, per-user rate-limits, token-budget enforcement, org-wide PII redaction → plugins.

Production readiness checklist

  • Persistence — DatabaseSessionService → managed Postgres (not ephemeral SQLite)
  • Secrets — out of the container; Cloud Run secrets / AWS Secrets Manager / etc.
  • Callbacks for guardrails (blocklist, PII, mocking-in-tests)
  • Plugins for audit logging, cost tracking, rate-limiting
  • Eval in CI — adk eval on every PR
  • Trace backend — Cloud Trace, Langfuse, Arize, or your own OTel collector
  • Auth — API gateway in front, or authenticated subnet

None of these are ADK-specific. They're what any Python service needs.
