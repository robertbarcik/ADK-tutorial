Multi-agent hierarchies

Two ways to compose agents with LLM-driven routing

sub_agents (transfer)  ·  AgentTool (consultant)

Three ways to combine agents

PatternControl flowWhen

The one question

Who is in charge of the conversation after the specialist finishes?

That is the only meaningful difference between the two patterns.

Pattern 1

sub_agents

The org-chart transfer. Specialist owns the response.

How it works

  • Coordinator has sub_agents=[...].
  • ADK automatically injects transfer_to_agent(agent_name=...) as a callable.
  • The coordinator's LLM emits transfer_to_agent('weather_specialist').
  • ADK transfers control to the named child. The child produces the final response.
  • The child remains active for follow-up turns. It transfers again to hand back.

Think org chart. The coordinator is the manager; the specialist takes the meeting.

Coordinator with sub_agents

greeter = LlmAgent(name="greeter",
    description="Handles greetings and casual chat.",
    instruction="Respond warmly in one short sentence.")

weather_specialist = LlmAgent(name="weather_specialist",
    description="Handles weather questions for any city.",
    instruction="Produce a plausible one-sentence weather report.")

coordinator = LlmAgent(
    name="coordinator",
    instruction="Delegate greetings to greeter, weather to weather_specialist.",
    sub_agents=[greeter, weather_specialist],   # ← here
)

The child's description= is what the coordinator's LLM reads to decide routing. Write descriptions for the model.

The event stream

USER: What's the weather in Prague?

[coordinator_subagents] → transfer_to_agent({'agent_name': 'weather_specialist'})
[weather_specialist]    The weather in Prague is partly cloudy with a gentle
                        breeze and a temperature of 15 degrees Celsius.
                        ^^^ final response comes from the SPECIALIST
Pattern 2

AgentTool

The consultant pattern. Coordinator stays in charge.

How it works

  • Wrap each specialist in AgentTool(agent=...).
  • Put those in the coordinator's tools=[...], not sub_agents=[...].
  • Coordinator's LLM emits a regular function call, the same mechanism as get_weather or search_tickets.
  • ADK runs the specialist, captures its output as a tool-response event.
  • The coordinator reads the response and produces the final reply itself.

Coordinator with AgentTool

from google.adk.tools.agent_tool import AgentTool

# Same specialists.
greeter = LlmAgent(name="greeter", description="...", instruction="...")
weather_specialist = LlmAgent(name="weather_specialist", ...)

coordinator = LlmAgent(
    name="coordinator",
    instruction="Call greeter or weather_specialist; wrap the result.",
    tools=[
        AgentTool(agent=greeter),
        AgentTool(agent=weather_specialist),
    ],
)

Specialists are in tools=, not sub_agents=. To the coordinator's LLM, they look like function tools.

The event stream — note the author

USER: What's the weather in Prague?

[coordinator_tools] → weather_specialist({'request': 'Prague'})
[tool_resp]            {'result': 'Prague will experience partly cloudy
                        skies with a high of 18 degrees Celsius today.'}
[coordinator_tools]    The weather in Prague will be partly cloudy with
                        a high of 18 degrees Celsius today.
                        ^^^ final response comes from the COORDINATOR,
                            wrapping the specialist's output

Tell-tale sign

Look at the author of the final response.

Specialist → transfer. Coordinator → consultant.

When to pick which

sub_agents — transfer

  • Specialist should own the dialog
  • Might take multiple turns before handing back
  • Topic shifts: the specialist is the right partner for the whole topic
  • User perceives talking to a specialist
vs

AgentTool — consultant

  • Specialist answers one question and steps back
  • Clean input/output contract
  • Coordinator composes specialist output with other sources
  • User perceives one assistant with specialists behind the scenes

Concrete examples

sub_agents scenario — IT support desk

Coordinator routes "laptop won't boot" to hardware specialist. Over the next five turns, hardware specialist walks user through diagnosis. That's an extended conversation the coordinator shouldn't mediate.

AgentTool scenario — coding assistant

Orchestrator wraps a code-analyzer, a docs-lookup, a test-runner. User asks "why is my test failing?". Orchestrator calls all three, synthesizes one answer. Each specialist contributes a single structured response.

Interlude · Agentic Design Patterns

Multi-agent decomposition

Every agent you add costs something.

Three costs of adding more agents

  1. Extra LLM calls. Every transfer or AgentTool call is an additional model invocation. Two-specialist system = 2+ calls per turn. Five specialists = 10+. Compounds latency and cost.
  2. Routing errors. Every routing decision is a chance to pick the wrong specialist. More specialists → wider miss surface.
  3. Context fragmentation. Each child has its own system prompt. Information you put in the coordinator doesn't automatically reach children. Specialists fail sometimes because they lack context the coordinator had.

Three tests before you decompose

Test 1 — Reuse

Will any specialist be used elsewhere, in a different product or different top-level agent? If yes, decomposition is worth it. If no, consider one agent with more tools.

Test 2 — Model heterogeneity

Does each specialist benefit from a different model? Routing on Haiku, resolving on Opus? If yes, separate agents let you mix per task. If all share one model, less payoff.

Test 3 — Instruction scale

Is a single system prompt getting unmanageable (500 lines with overlapping rules)? Breaking it up is legitimate. But if your prompt is 30 lines, don't split for sport.

If none of the three tests pass

Keep it to one agent with tools.

Multi-agent is the right answer sometimes. Not by default.
