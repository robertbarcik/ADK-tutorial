Why agents, why ADK

The four primitives you will see in every later module

Agent · Runner · Event · Session

What ADK is

A code-first Python framework for building LLM-driven agents. Google wrote it. Open source. 1.0 GA May 2025, now on v1.31. Python is the reference SDK; Java, Go, and TypeScript exist.

What ADK is not

  • Not a model. You bring your own — Gemini, Claude, GPT, Qwen, Gemma.
  • Not a cloud. Runs on your laptop, on Cloud Run, on AWS, on a Raspberry Pi.
  • Not a UI. It ships a dev UI (adk web), but the output is code you deploy.
  • Not a graph DSL. You write typed Python, not a JSON DAG.

Why a framework at all

The first time someone writes an "agent" by hand, they end up writing the same sixty lines every time:

  • A retry loop around the LLM call.
  • A JSON-shaped output parser that crashes on edge cases.
  • A manual conversation history that outgrows the context window.
  • A switch statement that dispatches tool calls to Python functions.
  • Error handling when the model asks for a tool that doesn't exist.

A framework lets you stop writing those sixty lines. You write the things that are actually yours — the instruction, the tools, the business logic — and the framework handles the rest.

The agent equation

LLM + instruction + tools + memory + a loop = agent

ADK gives you the loop and the plumbing. You bring the other four.

The four primitives

Agent
An LLM wired to a model, an instruction, and optional tools. You define one.
Runner
The event loop that drives the conversation. You call .run_async().
Event
Every message, tool call, tool response, and state change. You read them.
Session
The conversation's memory — event history plus a state dict. One per chat.

Every later concept — workflow agents, multi-agent hierarchies, callbacks, memory services, evaluation — composes on top of these four.

Primitive 1 — Agent

Four required arguments: name, model, description, instruction. An optional tools list. That's it.

from google.adk.agents import Agent
from google.adk.models.lite_llm import LiteLlm

greeter = Agent(
    name="greeter",
    model=LiteLlm(model="openrouter/google/gemini-2.5-flash-lite"),
    description="Greets the user in a friendly way.",
    instruction="You are a friendly greeter. Respond in one short sentence.",
)

The LiteLlm wrapper is what makes ADK vendor-neutral. Swap the model string and the rest doesn't change.

Primitive 2 — Runner

An agent on its own does nothing. The Runner wires it to a session service and hands you back an async event stream.

runner = Runner(agent=greeter, app_name="demo", session_service=sessions)

async for event in runner.run_async(
    user_id="student",
    session_id="s1",
    new_message=types.Content(role="user", parts=[types.Part(text="hi")]),
):
    print(event)

Think of the Runner as a game engine's main loop, and your agent as the entity it ticks.

Primitive 3 — Event

Every communication inside an agent run is an Event. This is the feature most frameworks skip and ADK gets right.

  • User message in → event.
  • Model text response → event.
  • Model decides to call a tool → event.
  • Tool returns a value → event.
  • Agent hands off to a sub-agent → event.
  • State changes → event.

Read the events and you can see exactly what the agent did and why. This is the debugger for agent work.

Primitive 4 — Session

A session holds the event history and a state dict, keyed by (app_name, user_id, session_id). Three session services ship with ADK:

ServiceBackingWhen
InMemorySessionServicePython dictDemos and tests
DatabaseSessionServiceSQLAlchemy (Postgres, SQLite)Self-hosted production
VertexAiSessionServiceGoogle CloudIf you're on Vertex

We'll use in-memory for M01–M07 and swap to database in M08 when memory becomes the point.

Add a tool

Tools are Python functions. The docstring and type hints are the JSON schema the model sees. No decorators, no config.

def get_weather(city: str) -> dict:
    """Look up today's weather for a city."""
    fake = {"Bratislava": "Sunny, 18C", "Prague": "Cloudy, 14C"}
    return {"city": city, "report": fake.get(city, "Unknown.")}

weather_agent = Agent(
    name="weather_agent",
    model=MODEL,
    instruction="Call get_weather and report what it returns. Be brief.",
    tools=[get_weather],
)

The visual version: adk web

Run adk web in a folder with your agent and it opens a chat UI with the same event stream rendered as a clickable timeline. Same data, friendlier for exploration.

Tip

Keep adk web open while you develop. When an agent misbehaves, its reason is almost always obvious from the timeline — a tool returned the wrong shape, an instruction was ambiguous, a state key was stale.

ADK vs. the obvious alternatives

LangGraph

  • Graph DSL; explicit nodes and edges.
  • Great for complex control flow, heavier for a simple agent.
  • ~34M monthly downloads.
vs

CrewAI

  • Role-playing DSL (Researcher, Writer).
  • Fast on demos, opinionated on metaphor.
  • ~44K stars.

ADK's pitch: typed Python, not a DSL. Explicit primitives, not metaphors. Smaller community (~18K stars, ~202 contributors) but the clearest event-level observability in the category.

"But it's a Google framework"

The single most common objection. It is a Google framework, and Google uses it to sell Gemini and Vertex. But the model abstraction is a one-line swap:

# Gemini via Google AI Studio
model = "gemini-2.5-flash"

# Claude via OpenRouter
model = LiteLlm(model="openrouter/anthropic/claude-haiku-4-5")

# GPT-4o-mini via OpenRouter
model = LiteLlm(model="openrouter/openai/gpt-4o-mini")

# Qwen3 running locally via Ollama
model = LiteLlm(model="ollama_chat/qwen3:8b")

Part 1 of this course uses LiteLLM against OpenRouter for exactly this reason. We only switch to direct Gemini in Part 2, where Gemini-only features earn it.
