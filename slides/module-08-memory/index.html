DatabaseSessionService + MemoryService + load_memory

Seven modules, one problem

InMemorySessionService loses everything on process restart.

Perfect for tutorials. Useless for production.

Two different time scales

ScalePrimitiveUse
Within one conversationSession state (M03)Current turn context; user: for cross-session within one user

The boundary matters. Session state handles "today's conversation". MemoryService handles "what did we talk about last month?"

Part 1 — Persistence

DatabaseSessionService

One-line swap. Sessions survive restarts.

The swap

# Demo (M01-M07): loses on process restart
session_service = InMemorySessionService()

# Production: persists to disk
session_service = DatabaseSessionService(
    db_url="sqlite+aiosqlite:///app.db"
)

# For real production: Postgres / MySQL
session_service = DatabaseSessionService(
    db_url="postgresql+asyncpg://user:pass@host/db"
)

Everything else is unchanged. Same Runner, same agents, same event stream.

Gotcha — the URL must be async

Do not use sqlite://

ADK's DatabaseSessionService uses SQLAlchemy's async engine. The plain sqlite:// scheme hits a sync driver and fails. You must use sqlite+aiosqlite://.

Install dependencies

pip install aiosqlite greenlet — aiosqlite is the async driver; greenlet is a transitive SQLAlchemy async requirement.

Part 2 — Long-term memory

MemoryService + load_memory

Explicit retrieval across unrelated sessions.

The shape

  1. During a conversation, things happen.
  2. You archive the session: await memory.add_session_to_memory(session).
  3. In a fresh session later, the agent has access to load_memory(query: str).
  4. The agent calls it; memory service returns matching snippets; the agent grounds its answer.

Archiving is deliberate. ADK does not auto-archive. You decide when a session becomes searchable history.

Two memory services ship

ServiceBackingWhen
InMemoryMemoryServicePython dictDemos (this notebook)

Memory Bank is the real-world path if you're on Google Cloud — it extracts facts, deduplicates, consolidates over time. For self-hosted production, you'd implement BaseMemoryService against Postgres + pgvector or similar.

Interlude · Agentic Design Patterns (revisited)

Skeptical Memory — with teeth

Long-term memory is a journal, not a cache.

The staleness problem at long horizons

Three months ago: user said they work at Acme Corp. Memory stored. Today: agent searches, finds it, uses it to ground a reply.

The user might have changed jobs. The memory is accurate as of the day it was stored. It is not accurate as of today. The agent, acting confidently on a three-month-old fact, is confidently wrong.

At long time horizons, staleness is the default, not the exception.

Three defensive patterns

1. Retrieve-and-verify for high stakes

Before irreversible actions, call a read-only tool to re-verify the retrieved fact. "Let me confirm — you're still at Acme, right?"

2. Stamp memories with recency

Store the date alongside every user:/app: write. Surface the recency to the model so it can distrust old facts.

3. Decay or consolidate

Memory Bank does this automatically. For InMemoryMemoryService, implement the policy yourself — delete or compress entries older than N days.

The framing

Long-term memory is a journal.

Every retrieved fact is a claim from when it was written. Not a fact that is true now.
