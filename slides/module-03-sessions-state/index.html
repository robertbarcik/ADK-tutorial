Sessions, State, Events, Artifacts

Where the conversation's memory actually lives

The prefix is the lifetime.

Stateless agent

A party trick.

Stateful agent

Infrastructure.

A session is two things

  • A list of events — the full ordered history of every message, tool call, tool response, and state mutation. Read-only from your code; ADK appends.
  • A state dict — mutable key-value storage for whatever the agent should remember between turns.

Identified by the triple (app_name, user_id, session_id). That triple is the primary key for every session in every session store.

Three session services

Same interface across all three. You swap the service; the agent code doesn't change.

The important part

State — with scope prefixes

Four scope rings, one 5-character prefix.

The state dict has four scope tiers

PrefixScopeSurvives
(none)This session onlyUntil the session is deleted
user:This user, across all their sessionsAs long as the user exists
app:Global across all users of this appAs long as the app exists
temp:This invocation onlyThrown away after the run

React state, but with persistence tiers baked into the key.

Writing state from a tool

def remember_favorite_color(color: str, tool_context: ToolContext) -> dict:
    """Record the user's favorite color for future sessions."""
    # user: prefix → survives beyond this session
    tool_context.state["user:favorite_color"] = color
    return {"status": "saved", "color": color}

Add tool_context: ToolContext as a parameter. ADK injects the running context. tool_context.state behaves like a dict; the assignment is recorded as an event and persisted.

The wow moment

Session 1  ─────────────────────────────────────
  USER:       My favorite color is teal.
  tool_call:  remember_favorite_color(color='teal')
  state ←     user:favorite_color = 'teal'

          ═════ session ends, new session starts ═════

Session 2  ─────────────────────────────────────
  state IS:   user:favorite_color = 'teal'    ← carries over!
  USER:       Hey, what's my favorite color?
  tool_call:  recall_favorite_color()
  tool_resp:  {'known': True, 'color': 'teal'}
  FINAL:      teal.

No database setup. No vector store. No custom embedding pipeline. Just a prefix convention on a dict key.

Three ways to write state

PatternPersists?Use for
output_key="last_response" on the agentYesCaching final reply; passing output between workflow steps
tool_context.state[key] = value in a toolYesWriting structured data during tool calls
session.state[key] = value on a fetched sessionNo!Avoid. Does not persist.

The rule

output_key= on the agent.
tool_context.state[...] in a tool.

Direct assignment to a returned session's .state does not round-trip. It silently fails to persist.

Part 2 of the module

Events and Artifacts

The session's ledger and its blob store.

Events — the session's immutable ledger

Every turn produces events; the session keeps them all. Walk session.events to audit what happened, replay a conversation, or feed it into an evaluation suite.

[ 0] user         text(My favorite color is teal.)
[ 1] color_agent  tool_call(remember_favorite_color)
[ 2] color_agent  tool_resp | state_delta(['user:favorite_color'])
[ 3] color_agent  text(Awesome! I'll remember...) | state_delta(['last_response'])

State is a projection of the event stream's state_delta entries. This is event sourcing, and it's how ADK can back a session with a database later without the agent noticing.

Artifacts — binary blobs outside events

Images, audio clips, PDFs, any payload you don't want to serialize into events. Analogy: Git LFS for agents — the pointer lives in the event stream; the payload lives in a separate store.

  • InMemoryArtifactService — demos and tests.
  • GcsArtifactService — Google Cloud Storage, for production.
  • Or roll your own BaseArtifactService — S3, Azure Blob, MinIO.

Skimmable for now. M13 (Live API voice agent) is where artifacts carry real weight.

Interlude · Agentic Design Patterns

Skeptical Memory

Stored state is a hint, not a fact.

Memory staleness is real

The demo looks clean because the state hasn't had time to go stale. In production, this is not how it works.

  • User's favorite color from three months ago? Probably still current.
  • User's current project? Maybe not — they might have moved on without telling the agent.
  • Tickets the agent "remembered" being open yesterday? Possibly all closed.
  • Server IP an MCP tool cached? Could have been reassigned.

Stored memory is a hint. Not a fact.

Three guidelines from the publication

  1. Prefer retrieval over recall for high-stakes decisions. Before the agent sends an email, charges a card, or deploys code, it should call a read-only tool to re-verify — not trust its own stored state.
  2. Scope aggressively. temp: for scratchpads, unprefixed for per-session, user: only for things you're confident change only with explicit user action, app: only for genuinely immutable configuration.
  3. Log a reason when you write user: or app: state. Months from now you will debug an agent acting on six-month-old memory. The one-line "why did this get stored" note saves hours.

The pattern has a name: Skeptical Memory. Treat your own stored context as unverified until proven otherwise.
