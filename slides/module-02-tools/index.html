Tools as verbs

Four flavors, one mental model, one design rule to carry forward

FunctionTool · OpenAPI · MCP · AgentTool

Without tools

An agent is a chatbot.

With tools

An agent is software.

The tool mental model

┌─────────────┐   "I need to know X"    ┌─────────────┐
│     LLM     │────────────────────────▶│     ADK     │
│   decides   │                         │  dispatch   │
└─────────────┘                         └──────┬──────┘
       ▲                                       │
       │  "X is {...}"                         ▼
       │                                 ┌─────────────┐
       └─────────────────────────────────│  your tool  │
                                         │ (any flavor)│
                                         └─────────────┘

The model sees a schema (tool name, description, argument types) and decides when to call and with what arguments. ADK handles dispatch: find the code, call it, wrap the return, feed it back as a tool-response event.

Four flavors differ only in two things

FlavorSchema comes fromCode lives in
FunctionToolDocstring + type hintsYour Python file
OpenAPIToolsetAn OpenAPI specA remote HTTP API
McpToolsetMCP server's list_toolsA separate process
AgentToolAnother agent's name + descriptionThat other agent

Same abstraction to the model. Different integration targets. Build one of each.

Flavor 1

FunctionTool

Plain Python functions.

The docstring is the schema

  • ADK reads your function's docstring + type hints.
  • It builds the JSON schema the LLM provider expects.
  • Three consequences:
Tip
  • Write the docstring for the model, not for a human reviewer. The model has no channel to ask you what a parameter means.
  • Type hints are load-bearing. Missing hints degrade to string.
  • Return a JSON-serializable dict or string. Not a custom class, not a NumPy array.

A FunctionTool with a rich docstring

def get_weather(city: str, units: str = "celsius") -> dict:
    """Look up today's weather for a city.

    Args:
        city: The city name in English (e.g. "Prague", "Munich").
        units: Either "celsius" (default) or "fahrenheit". Use
            "fahrenheit" only if the user explicitly asks for it.
    """
    ...

The Args: block becomes the parameter descriptions. str becomes "type": "string". The default value becomes "required": false.

Flavor 2

OpenAPIToolset

Consume an entire REST API.

When your target is a REST API with a spec

Don't hand-write a FunctionTool for every endpoint. Hand ADK the OpenAPI spec; get N tools automatically.

  • The web frontend already uses this spec. The agent should too.
  • Works with any spec: JSON or YAML, dict or string.
  • ADK snake-cases the operationId: getLatestRate becomes get_latest_rate.

Frankfurter currency API — three lines to integrate

fx_toolset = OpenAPIToolset(spec_dict=FRANKFURTER_SPEC)

fx_agent = LlmAgent(
    ...,
    tools=[fx_toolset],
)

The spec lives in a dict (or a JSON/YAML string). Every path becomes a tool. No per-endpoint glue code.

Flavor 3

McpToolset

Talk to a separate tool server.

MCP in one paragraph

Model Context Protocol. Anthropic's standard for exposing tools to agents, donated to the Linux Foundation in December 2025. A de facto protocol for agent-to-tool communication across the industry. An MCP server is a separate process; your agent connects over stdio or HTTP and uses its tools as if they were local.

Why this matters

Your MCP server can be written in any language, run on any machine, own any state — database connections, API credentials, caches. The agent doesn't care. It speaks the protocol; the tools just work.

Connect to an existing MCP server

ticket_toolset = McpToolset(
    connection_params=StdioConnectionParams(
        server_params=StdioServerParameters(
            command=sys.executable,
            args=["mcp_servers/ticket_mcp_server.py"],
        ),
        timeout=20,
    )
)

ticket_agent = LlmAgent(..., tools=[ticket_toolset])

ADK spawns the server, speaks MCP, and discovers its tools. Five tools appear with no extra code.

Flavor 4

AgentTool

Wrap an agent as a tool.

The consultant pattern

AgentTool

Parent calls the specialist like a function. Parent stays in charge. Child answers, hands control back.

When: child has a clean I/O contract; you want visibility in the parent's event stream.

vs

sub_agents

Parent transfers to the child. Child owns the conversation until it decides to hand back.

When: child should own multiple turns of the dialog.

M06 will do this comparison in detail. Today: focus on the consultant pattern.

A translator, called like a function

translator = LlmAgent(
    name="translator",
    description="Translates English to Slovak. Input: phrase. Output: translation.",
    instruction="You are a translation tool. Output the Slovak translation only.",
    ...
)

orchestrator = LlmAgent(
    name="orchestrator",
    instruction="Call the translator when the user asks for a translation.",
    tools=[AgentTool(agent=translator)],
)

Interlude · Agentic Design Patterns

Risk-based tool design

Not all tools are equal. Treat them like they aren't.

Categorize tools by blast radius

TierCharacteristicExampleGuard
Read-onlyNo external changeget_weather, search_ticketsNone
Mutating, reversibleWrite, easy to undocreate_ticket, send_draft_emailLog every call
Mutating, irreversibleHard to roll backcharge_card, post_to_slackExplicit confirmation
CatastrophicLoud, multi-user, destructivedrop_database, delete_userHuman in the loop

The temptation is to treat every tool the same because the framework does. Don't.

The rule

Put the guard in the tool code.

Not in the instruction. An instruction is a polite request the model can ignore. Code is a wall.

A delete tool with a confirmation gate

def delete_ticket(ticket_id: str, confirmation_token: str = "") -> dict:
    """Delete a support ticket. IRREVERSIBLE.

    Args:
        ticket_id: The ticket to delete.
        confirmation_token: Must equal "CONFIRM_DELETE_<id>".
            Empty or wrong → returns a preview, does nothing.
    """
    expected = f"CONFIRM_DELETE_{ticket_id}"
    if confirmation_token != expected:
        return {"status": "preview", "message": f"Pass token={expected} to proceed."}
    ...

Choosing a flavor

If you have...Use...
A Python function that needs to run in-processFunctionTool
An existing REST API with an OpenAPI specOpenAPIToolset
A tool server written in any language with its own stateMcpToolset
A specialist sub-agent the parent should call like a functionAgentTool

The FunctionTool is the default. Reach for the others when you have a specific reason.

Gotchas worth knowing now

Built-in tools don't mix

Google Search, code execution, and Vertex Search can't coexist with other tools in the same agent. Exception for Search in ADK ≥ 1.16: bypass_multi_tools_limit=True. Workaround: wrap each as a sub-agent.

MCP stdio in Jupyter / Colab

Jupyter replaces sys.stderr with an object without a .fileno(), which breaks subprocess spawn. Patch sys.stderr to a real fd before importing McpToolset. (The notebook does this automatically.)

LiteLLM + tool-calls + streaming

Known flaky on non-Gemini models. Default stream=False for demos on OpenRouter. (ADK does this out of the box.)

What to carry forward

Tools come in four flavors. Same abstraction to the model; different integration targets.

And: blast radius matters. Put the guard in the tool code, not in the instruction.
