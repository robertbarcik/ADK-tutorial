Evaluation

Beyond eyeballing the event stream

Up to now

"does the agent work?"

answered by

eyeballing the event stream.

This module stops doing that.

Two built-in metrics

MetricAsksScaleDefault
tool_trajectory_avg_scoreRight tools, right order, right args?0-11.0 (strict)
response_match_scoreFinal text close to expected?0-1 (ROUGE-1)0.8

Trajectory is the novel one. Most eval frameworks score outputs only. ADK weighting how the agent got there matches tool-heavy reality.

Why trajectory matters

A correct answer via the wrong reasoning
is a bug waiting to happen.

Chat, save, tweak, re-run. Build the evalset incrementally as you iterate on the agent.

A minimal .test.json

{
  "eval_cases": [{
    "eval_id": "case_prague",
    "conversation": [{
      "invocation_id": "inv-1",
      "user_content": {
        "parts": [{"text": "What is the weather in Prague?"}],
        "role": "user"
      },
      "final_response": {
        "parts": [{"text": "The weather in Prague is cloudy and 14 degrees Celsius."}],
        "role": "model"
      },
      "intermediate_data": {
        "tool_uses": [{"name": "get_weather", "args": {"city": "Prague"}}]
      }
    }]
  }]
}

Declares expected user input, expected tool trajectory, expected final response.

Where ROUGE-1 breaks

expected:  "The weather in Prague is cloudy and 14 degrees Celsius."
actual:    "The weather in Prague is cloudy, and the temperature is 14 degrees Celsius."

response_match_score: 0.87  (threshold 0.95)  → FAIL

Same information. Different words. ROUGE-1 counts overlapping unigrams; stylistic variation costs you points.

Trajectory score was 1.0: the agent called the right tool. The failure is pure wording.

Trajectory testing is useful.
ROUGE-1 response matching is weak.

ROUGE-1 punishes legitimate stylistic variation. Don't rely on it for production.

Working range in practice

// test_config.json next to your .test.json
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,    // keep strict
    "response_match_score": 0.6          // permissive
  }
}

0.6-0.7 for short responses. For long-form text, response_match_score is the wrong metric entirely.

Dropping the threshold is not a win. The real upgrade is LLM-as-judge.

LLM-as-judge — the real upgrade

# Pseudocode; ADK 1.29+ ships Gen AI Evaluation Service for this
def judge(prompt, expected, actual) -> float:
    response = judge_llm(
        f"Is this a reasonable answer?\n"
        f"Prompt: {prompt}\n"
        f"Expected: {expected}\n"
        f"Actual: {actual}\n"
        f"Score 0-1 on semantic correctness."
    )
    return float(response.strip())

Different framing: trajectory asks did the agent do the right things. LLM-judge asks did it say the right thing.

The full picture

LayerAnswersCost
Trajectory scoreDid it call the right tools in the right order?Free, structural check
ROUGE-1 response matchIs the text lexically close to expected?Free, but weak signal
LLM-as-judgeIs the answer semantically correct?One extra LLM call per test
Human reviewIs the answer actually good?Expensive. Unavoidable at the tail.

Combine all four at different cadences. Trajectory on every PR, ROUGE-1 for regressions, LLM-judge nightly, human review for flagged cases.

Production gotcha

adk eval writes to agents_dir

In locked-down containers with read-only root filesystems (common in Kubernetes), the eval run hits PermissionError. Upstream: adk-python #3887.

Workaround: make agents_dir writable during eval, OR run eval outside the deployed image. CI job against the same code, developer machine, separate eval pipeline.

What to carry forward

Test trajectory strictly.
Test response with LLM-as-judge.
Don't trust ROUGE-1 past the sanity check.
